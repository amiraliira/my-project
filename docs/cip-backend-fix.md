# اصلاح محاسبهٔ کارکرد و دسترس‌پذیری شرکت — cip.1

تاریخ: 2026-10-25. مبنا: سورس 2.0.0-rc.10 / handoff.1.

## نتیجه

طبق تصمیم صریح کاربر، CIP جزو کارکرد است و فقط توقف فنی دسترس‌پذیری را کم می‌کند. در نسخهٔ اصلاح‌شده:

- زمان کارکرد شرکت = کل مدت شیفت − توقف فنی.
- دسترس‌پذیری فنی = زمان کارکرد شرکت ÷ کل مدت شیفت × ۱۰۰.
- زمان CIP و دیگر بازه‌های planned و nontechnical برای بررسی و گزارش حفظ می‌شوند، ولی از مبنای فنی کارکرد و دسترس‌پذیری کم نمی‌شوند.
- مثال: شیفت۸ساعت، CIP یک ساعت و خرابی فنی یک ساعت → کارکرد۷ساعت، دسترس‌پذیری۸۷٫۵٪.
- شیفت فقط CIP یا فقط زمان غیرفنی، بدون خرابی فنی → دسترس‌پذیری۱۰۰٪. تولید صفر همچنان OEE صفر می‌دهد و با دسترس‌پذیری۱۰۰٪ یکی نیست.

نسخهٔ فرمول از pak-oee-count-2 به pak-oee-count-3 تغییر کرده است. شمارهٔ برنامهٔ پایه rc10 حفظ شده و شناسهٔ اصلاح مستقل cip.1 است.

## دامنهٔ دقیق

در داده و API فعلی فیلد مستقل CIP نداریم؛ گروه planned در رابط شامل CIP، شست‌وشو و تعویض است. هیچ تشخیص حدسی از متن آزاد علت اضافه نشده است. برای اجرای قاعدهٔ «فقط توقف فنی»، تمام زمان‌های غیرفنی/برنامه‌ریزی‌شده از نظر این شاخص فنی جزو کارکرد شرکت‌اند. مقادیر جداگانهٔ آن‌ها حذف نشده‌اند.

runMinutes، productionMinutes و شاخص‌های وابسته مانند نرخ واقعی، MTBF، کارایی سرعت و OEE از مبنای تازه استفاده می‌کنند. quality و تعدادها تغییر نکرده‌اند. OEE و technicalOee در این قرارداد بر کل شیفت محاسبه می‌شوند و availability و technicalAvailability نیز برابرند. همان نام‌های API برای سازگاری حفظ شده‌اند.

## گزارش‌های قبلی و شواهد

facts زمان‌های محاسبه‌شده را ذخیره می‌کرد. فقط تغییر محاسبهٔ فرم تازه کافی نبود؛ روز/جزئیات از سند اصلی دوباره محاسبه می‌شد ولی جمع دوره از facts قدیمی می‌آمد. aggregate اکنون زمان‌ها را از مدت شیفت و توقف فنی بازسازی می‌کند تا دادهٔ قدیمی و جدید در جمع دوره یک قاعده داشته باشند.

هیچ UPDATE، migration یا بازنویسی سوابق برای این اصلاح لازم نیست. اطلاعات ثبت‌شده و revisionهای بایگانی تغییر نمی‌کنند. نمایش history عمداً شواهد و فرمول تاریخی ذخیره‌شده را نشان می‌دهد؛ نمایش روز/گزارش جاری با فرمول۳ محاسبه می‌شود.

## فایل‌های اجرایی و آزمون

- backend/src/pak_maintenance/oee_metrics.py: اصلاح محاسبه و سازگاری facts قدیمی.
- backend/tests/test_oee_metrics.py: مثال عددی، CIP کامل، غیرفنی، شیفت شب، نبود تولید و جمع دوره.
- backend/tests/test_oee_cip_report.py: بررسی مسیر واقعی سرویس گزارش با اتصال ساختگیِ فقط‌خواندنی و حفظ شواهد history.
- backend/tests/test_oee_service.py: یک سناریوی PostgreSQL واقعی برای سازگاری روز/دوره با facts قدیمی افزوده شده است.

۲۱ آزمون محاسبات و مسیر گزارش در محیط حاضر پاس شد؛ شکست و skip در این مجموعه صفر بود. بازبین مستقل همین۲۱ مورد را تکرار و تأیید کرد؛ تعدادها با هم جمع نمی‌شوند. تست PostgreSQL تازه به‌دلیل آماده‌نبودن محیط ایزوله و وابستگی‌های native در این سیستم اجرا نشده است.

اجرای آزمون‌های مستقل از PostgreSQL از ریشهٔ سورس روی Linux:

```sh
PYTHONPATH="$PWD/backend/src:$PWD/backend/tests" python -B -m unittest \
  test_oee_metrics test_oee_cip_report
```

گزارش ماشینی و خروجی کامل در docs/verification/cip-fix-review.json و cip-fix-tests.txt است. گزارش‌های rc10 قبلی داخل همان پوشه شواهد نسخهٔ پایه‌اند و پذیرش تازهٔ این اصلاح محسوب نمی‌شوند.

## فرانت و وضعیت استقرار

اصلاح حاضر بک‌اند است. فرانت عددها را از API می‌گیرد و فرمول موازی در آن تغییر داده نشده است. متن بخش بازشوندهٔ «مبنای محاسبه و سایر شاخص‌ها» در فرانت موجود هنوز دربارهٔ کسر planned توضیح قدیمی دارد؛ آن متن با سیاست جدید منطبق نیست و در این بسته تغییر/بازسازی نشده است. خروجی dist همان خروجی پایه است. این محدودیت باید هنگام تحویل رابط بعدی رفع شود؛ اعداد API اصلاح شده‌اند.

این بسته روی سرور شرکت نصب نشده و آزمون ورود، PostgreSQL و شبکهٔ شرکت انجام نشده است. نصب روی checkout تغییرکردهٔ شرکت نباید با جایگزینی کورکورانهٔ کل پوشه انجام شود؛ فایل patch برای بازبینی اختلاف همراه است. دادهٔ baseline یا reset جزو این اصلاح نیست.

## سلامت تحویل

source-manifest.json برای تمام فایل‌های این خروجی دوباره تولید شده و backend-patch.json شناسه، فرمول و هش مبنای فایل اجرایی را ثبت می‌کند. فایل ZIP سورس کامل شامل دادهٔ شرکت، dump، رمز، گواهی، runtime یا وابستگی نصب‌شده نیست. فایل PAK-Backend-CIP-2026-10-25.patch اختلاف فایل‌ها و manifest را نسبت به سورس اصلی نشان می‌دهد. ابزار verify_source.py در محیط محدود فعلی Windows به WinError5 هنگام resolve مسیر برخورد کرد؛ کنترل مستقل CRC و تمام هش‌ها/اندازه‌های manifest در ZIP موفق بود. این محدودیت محیط به معنی خرابی بسته نیست.
